## Les modes de travail
type: titre

Le même modèle, quatre espaces différents.
Vous en ouvrez un seul, et vous passez à côté du reste.

::: notes
Module court mais rentable : la plupart des gens font tout dans le chat web, y compris ce qui devrait vivre ailleurs.

Question d'ouverture : « quand vous ouvrez l'outil le matin, vous cliquez où ? »
:::

---

## Quatre espaces, quatre usages
type: concept

| Espace | Pour quoi | Ce qui persiste |
| --- | --- | --- |
| **Chat** | Question rapide, brainstorm | Rien |
| **Projects** | Un dossier suivi dans la durée | Instructions + fichiers de référence |
| **Cowork** | Produire des livrables, manipuler des fichiers | Fichiers de travail |
| **Code** | Terminal, dépôts, automatisation | Le dépôt lui-même |

La colonne de droite est celle qui compte : **ce qui persiste détermine ce que vous n'aurez pas à réexpliquer.**

::: notes
Insister sur Projects, largement sous-utilisé. Un Project, ce sont des instructions permanentes plus des fichiers que l'outil relit à chaque conversation du projet.

Pour un usage commercial : un Project par client ou par mandat, pas un Project fourre-tout.
:::

---

## Ce que « persiste » veut dire exactement
type: concept

Dans un Project, deux choses sont rechargées à **chaque** nouvelle conversation :

- **Les instructions** — un texte permanent : qui vous êtes, ce qu'on vend à ce client, comment vous écrivez.
- **Les fichiers de référence** — les documents que l'outil peut relire à tout moment.

Ce qui **ne** persiste **pas** : l'historique des conversations précédentes du projet. Chaque conversation reste indépendante.

> Un Project est un décor qu'on replante à chaque conversation, pas un carnet de ce qui s'est dit.

::: notes
Malentendu numéro un sur Projects : les gens croient que l'outil se souvient de leurs échanges de la semaine dernière. Non — il relit les instructions et les fichiers, pas les conversations.

D'où la conséquence pratique : ce qui doit survivre à une conversation doit être **écrit dans un fichier**, pas dit dans le fil. C'est exactement le sujet du module 6.
:::

## Le réflexe à prendre
type: concept

Avant d'ouvrir une conversation, une seule question :

> **Est-ce que je vais refaire ça ?**

- **Non, une seule fois** → chat, et on n'en parle plus.
- **Oui, régulièrement, sur le même dossier** → un Project.
- **Oui, et ça produit un fichier** → Cowork.
- **Oui, et ça devrait tourner sans moi** → une tâche planifiée (module 9).

::: notes
C'est la règle de tri la plus rentable de la journée. La faire appliquer tout de suite sur trois usages réels du participant.

Si un usage tombe dans deux cases, c'est qu'il empile deux tâches. Le découper — ça prépare le module 4.
:::

## Le coût du mauvais espace
type: piege

Travailler dans le chat ce qui relève d'un Project a trois effets, tous invisibles au début :

- Vous **réexpliquez** votre contexte à chaque conversation, quinze à vingt lignes à chaque fois.
- Vos réglages de ton et de format sont **incohérents** d'une fois sur l'autre, parce que vous ne les retapez jamais à l'identique.
- Le travail n'est **pas transmissible** : personne d'autre ne peut reprendre le dossier.

Le troisième point est celui qui coûte le plus cher en entreprise.

::: notes
Le troisième point est l'argument à sortir devant un dirigeant : un Project bien tenu, c'est du travail qu'un collègue peut reprendre. Un historique de chat, non.

C'est aussi ce qui transforme l'IA d'un gadget individuel en outil d'équipe.
:::

## Le desktop plutôt que le web
type: concept

L'application de bureau donne accès à ce que le navigateur n'a pas :

- Les **fichiers locaux** et les dossiers de travail
- Les **connecteurs** vers {{client.mail}}, {{client.agenda}}, {{client.crm}}
- Les **tâches planifiées** qui tournent sans vous
- Les **skills** et leur exécution

Le chat web sert à jeter un œil. Le travail se fait dans l'application.

::: notes
Vérifier ici, concrètement : l'app desktop est-elle installée ? Le plan est-il le bon ? Si non, l'installer maintenant, sinon la moitié de la journée tombe à plat.

Ne pas passer à la suite sans que ce soit fait. C'est le prérequis matériel des modules 7 et 9.
:::

## Où ranger quoi
type: atelier
livrable: Une carte des espaces de travail, avec un Project créé et ses instructions rédigées

Sur vos usages réels :

1. Listez cinq choses que vous avez demandées à l'outil cette semaine.
2. Classez-les dans les quatre espaces.
3. Créez le Project du dossier qui revient le plus souvent.
4. Rédigez ses instructions permanentes : qui vous êtes, ce dossier, comment vous écrivez.
5. Mettez-y les deux ou trois fichiers de référence qui le décrivent.
6. Ouvrez une conversation neuve dedans et vérifiez qu'il n'a plus besoin qu'on lui explique le dossier.

::: notes
Pour {{client.prenom}} : le Project du mandat principal. Y déposer le contexte client et les contraintes connues.

L'étape 6 est la validation : si l'outil repose une question dont la réponse est dans les instructions, c'est que les instructions sont mal écrites. On les corrigera au module 6.

Ne pas chercher l'exhaustivité maintenant, on remplira ce Project plus tard.
:::

## À retenir
type: recap

- Quatre espaces : Chat, Projects, Cowork, Code. Ce qui les distingue, c'est ce qui persiste.
- Un Project recharge des instructions et des fichiers, pas l'historique des conversations.
- La question de tri : est-ce que je vais refaire ça ?
- Un Project par dossier suivi, pas un Project fourre-tout.
- Le mauvais espace coûte du temps, de la cohérence, et rend le travail intransmissible.
- L'application de bureau, pas le chat web.
