## Tâches planifiées
type: titre

Tant que vous êtes le seul déclencheur,
vous êtes le plafond.

::: notes
C'est le module du passage au niveau 2. Tout ce qui précède y converge : prompt propre (3), contexte cadré (4), mémoire (5), connecteurs (6), skill (7).
:::

---

## La règle des deux fois
type: concept

> Toute tâche faite **deux fois par semaine** doit devenir une tâche planifiée ou une skill.

Pas parce qu'elle prend du temps. Parce qu'elle prend de **l'attention** : il faut y penser, choisir le moment, retrouver le contexte.

La tâche planifiée supprime la charge mentale avant de supprimer le temps.

::: notes
Argument à privilégier chez un dirigeant : ce n'est pas un gain de productivité, c'est un gain de disponibilité mentale.

Faire lister trois tâches qui passent la règle des deux fois.
:::

---

## La règle d'architecture
type: concept

La seule décision structurante de tout le dispositif :

| Ce que ça touche | Mode |
| --- | --- |
| **Interne** — un rapport, une synthèse, une todo, une veille | Automatisation complète |
| **Externe** — un mail, un message, une écriture dans {{client.crm}} | Brouillon à valider |

Rien ne part vers un tiers sans qu'un humain ait lu.

::: notes
Poser cette règle comme non négociable, et expliquer pourquoi : une erreur interne se corrige en silence, une erreur externe se paie en crédibilité.

C'est aussi la réponse à l'objection « et si ça dit une bêtise à un client ? ».
:::

## L'anatomie d'une tâche planifiée
type: concept

- **Un déclencheur** — une heure, un jour, une fréquence
- **Des sources** — celles cadrées au module 4
- **Une consigne** — le prompt en quatre blocs, ou une skill
- **Une destination** — un fichier, un brouillon, un message
- **Un mode de défaillance** — que se passe-t-il si une source manque ?

Le dernier point est celui qu'on oublie, et c'est celui qui fait qu'une tâche tourne six mois ou casse en trois semaines.

::: notes
Revenir sur la première tentative ratée du participant, s'il y en a eu une, et l'analyser avec cette grille. Il manquait presque toujours les sources ou le mode de défaillance.
:::

## Commencer petit, et interne
type: concept

La première tâche planifiée doit être :

1. **Interne** — personne d'extérieur ne la voit
2. **Vérifiable** — vous savez dire tout de suite si le résultat est bon
3. **Utile même imparfaite** — un résumé à 80 % rend service, un devis à 80 % non
4. **Hebdomadaire ou mensuelle** — assez fréquente pour être corrigée, assez rare pour ne pas noyer

Le briefing du matin et le bilan mensuel cochent les quatre.

::: notes
Refuser gentiment si le participant veut commencer par de l'envoi automatique de mails de prospection. C'est le meilleur moyen de casser la confiance au premier essai.
:::

## Monter la première tâche
type: demo

En direct, sur {{client.cas}} :

- Reprendre la liste de sources écrite au module 4
- Écrire la consigne, avec le mode de défaillance explicite
- Choisir la fréquence et l'heure
- Envoyer le résultat dans un fichier, pas dans un mail
- La déclencher une fois à la main pour voir le résultat

::: notes
Le déclenchement manuel du premier tour est essentiel : personne n'accepte d'attendre le mois suivant pour savoir si ça marche.

Prévoir que le premier résultat sera moyen. C'est normal, et c'est l'occasion de montrer la boucle de correction.
:::

## Corriger une tâche qui dérape
type: concept

Trois symptômes, trois causes :

| Symptôme | Cause presque toujours |
| --- | --- |
| Le résultat est générique | Contexte manquant, pas de second cerveau branché |
| Il invente des chiffres | Source absente et pas de mode de défaillance |
| Il oublie la moitié | Trop de tâches dans une seule consigne |

Aucune de ces causes n'est dans le modèle. Toutes sont dans la conception.

::: notes
Table utile à photographier. Elle sert de grille de dépannage après la formation, quand je ne suis plus là.
:::

## Mettre en place son flux
type: atelier
livrable: Une tâche planifiée qui tourne, testée une fois à la main

1. Choisissez une tâche interne, vérifiable, hebdomadaire ou mensuelle.
2. Écrivez les sources, la consigne, la destination.
3. Ajoutez la phrase « si une source manque, alors… ».
4. Déclenchez-la une fois à la main.
5. Corrigez la consigne d'après ce qui est sorti.
6. Programmez-la.

::: notes
Ne pas quitter le module sans que la tâche soit réellement programmée. Une tâche « qu'on programmera plus tard » n'est jamais programmée.
:::

## À retenir
type: recap

- Deux fois par semaine : ça devient une tâche planifiée ou une skill.
- Interne en automatique, externe en brouillon à valider. Jamais l'inverse.
- Cinq pièces : déclencheur, sources, consigne, destination, mode de défaillance.
- La première tâche : interne, vérifiable, utile même imparfaite.
- Quand ça dérape, le problème est dans la conception, pas dans le modèle.
